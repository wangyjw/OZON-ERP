## 一、目标与结论

**目标**：打通「插件采集 → 采集箱管理 → 店铺授权绑定 → 一键发布 → 状态回写」的最小可用闭环（MVP），确保一条 1688/Ozon 商品从采集到出现在 Ozon 店铺后台的全流程无需碰代码、失败可诊断。

**总体结论**：

| 链路 | 现状 | 结论 |
|---|---|---|
| 采集商品 | 扩展 9+ 平台扫描器 + 后端清洗/去重/类目匹配，链路完整 | 🟡 可用；缺采集箱检索的平台筛选参数、清空接口、列表字段修正 |
| 绑定 Ozon 店铺 | 双通道（API Key 表单 + 扩展 Cookie 桥接）已入库 | ❌ **无真实凭证校验**——添加/刷新授权只改本地状态，从不调 Ozon 验证，填错 Key 要到发布时才暴露 |
| 发布商品 | 任务化异步发布管线完备（限流/图片转存/属性组装/状态轮询/重试/断点续传） | ❌ 采集箱直发链路可用但缺**发布前置校验**；**上架记录页提交发布必失败**（v2 复检确认的 P0 bug）；发布成功不回写店铺字段 |

**优先级排序**：🐛 上架记录提交 bug 修复（半天，可先行热修）✅ **已完成** > 绑店真实校验（M1）> 发布前置校验（M2）> 采集箱补齐（M3）。理由：上架记录提交是确定性断裂（改两行即修）；绑店是发布的前置依赖，凭证不真实则一切发布皆失败；前置校验把发布失败从「异步任务失败」提前到「点击时拦截」。

## 四、详细设计

### 4.1 M1：绑定 Ozon 店铺——凭证真实校验闭环 ⭐ 最高优先级

**问题**：添加店铺时不验证 Client-Id/Api-Key，`refresh-auth` 只把本地 `auth_status` 置 `active`（`store_routes.py:219-231`）。填错凭证的店铺在界面上显示「已授权」，直到发布任务异步失败才暴露，且错误信息是 Ozon 的 401 原文，用户无从定位是哪一步的问题。

**设计**：新增店铺校验服务，接入添加/刷新/发布三个时点，形成「校验 → 回填 → 失效反标」闭环。

#### 4.1.1 后端：新增 Ozon 店铺信息接口封装

```python
# backend/services/ozon_api.py 新增
def get_store_info(client_id=None, api_key=None):
    """调用 Ozon 店铺信息接口验证凭证并获取店铺真实信息

    优先 POST /v1/seller/info（官方 SellerAPI_SellerInfo，返回 company.{name,currency}，
    不返回店铺数字 ID，因此用户手填的 store_id 保持不变）；
    若该端点 404/405（版本变动），降级用 POST /v3/product/list {"limit": 1}
    ——任何已鉴权轻量接口返回 200 即证明凭证有效，401/403 即无效。
    返回: {'store_id': None, 'name': ..., 'status': ...}，失败抛 OzonAPIError(带状态码)
    """
```

> 说明：Ozon Seller API 各版本端点路径有变动，实现时以官方文档为准；降级方案（用任意已鉴权接口探测）与现有 `_call_ozon_api`（`ozon_api.py:69`）完全兼容，零额外依赖。

#### 4.1.2 后端：新增校验路由 + 接入三个时点

```
POST /api/stores/verify        # 统一校验入口
  body: { storePk }            # 已有店铺校验
     或 { clientId, apiKey }   # 添加店铺前的预检（不落库）
  返回: { valid: true/false, storeName, ozonStoreId, errorCode, message }
```

| 接入时点 | 改动 | 行为 |
|---|---|---|
| 添加店铺 | `create_store`（`store_routes.py:69`）保存后自动调用 verify | 成功：`auth_status='active'`、`auth_time=now`、回填 `store_id`（若用户手填与 Ozon 返回不一致，以 Ozon 为准并提示）；失败：保存但置 `expired` + 返回具体原因（401 密钥错误/403 无权限/网络超时） |
| 刷新授权 | `refresh_auth`（`store_routes.py:219`）改为真实校验 | 同上；彻底去掉「无验证直接置 active」 |
| 发布失败反标 | `_publish_product_async`（`publish_service.py:2429`）捕获 `OzonAPIError` 时 | `status_code in (401, 403)` → `Store.update(auth_status='expired')`，错误消息写入店铺备注字段，前端店铺列表即时红标 |

> 注意：`stores.auth_status` 受 CHECK 约束限制为 `('active','expired','pending','disabled')`（`schema.sql:30`），凭证失效统一复用 `expired`，不新增枚举值。

#### 4.1.3 数据库变更

```sql
-- backend/schema.sql stores 表新增两列 + backend/db.py _run_migrations() 追加
ALTER TABLE stores ADD COLUMN verify_time TEXT;     -- 最后一次真实校验时间
ALTER TABLE stores ADD COLUMN last_auth_error TEXT; -- 最后一次校验/发布失败的凭证错误
```

迁移沿用现有模式（`db.py` 已有 `PRAGMA table_info` + `ADD COLUMN` 的幂等迁移，参照 `seller_cookies` 列的加法，`db.py:65-69`）。

#### 4.1.4 前端改动（`frontend/js/pages/store.js`）

1. 添加店铺弹窗：提交后展示校验结果；`expired` 时错误内联显示（保留表单数据供修改重提，不关弹窗）。
2. 店铺列表：`auth_status='expired'` 行红色标记 + 「重新授权」快捷按钮（回填 Client-Id 打开编辑弹窗）；新增「最后校验时间」列（`verify_time`）。
3. 发布弹窗（`collect.js:4670` 店铺选择弹窗、扩展 `publish-modal.js`）：`expired` 店铺置灰不可选，标注「凭证失效，请先重新授权」。

#### 4.1.5 Cookie 通道定位（明确边界，不扩大范围）

Cookie 绑定（`/stores/set_cookies`）服务于 seller.ozon.ru 桥接场景（扩展借权操作），**发布链路只走 API Key**（Ozon 官方刊登仅支持 API）。设计上明确：`auth_type='cookie'` 的店铺在发布时给出明确提示「Cookie 授权店铺不支持 API 发布，请补充 Client-Id/Api-Key」，而不是让它进任务后 401 失败。

### 4.2 M2：发布商品——发布前置校验（preflight）✅ 已实施（v2.3）

**问题**：`POST /api/publish`（`publish_routes.py:13`）只校验商品存在即建任务；缺类目、缺必填属性、图片不可公网访问、店铺凭证失效等问题都在异步执行时才失败。虽然任务错误会透出（`task_details`），但用户已经历「提交→等待→失败→查看错误→重新编辑→再提交」的长循环。

**设计**：新增同步预检接口，发布确认弹窗先调用，把可预防的失败全部前置到点击瞬间。

```
POST /api/publish/preflight
  body: { productIds: [...], storeId: "..." }
  返回: {
    storeReady: bool, storeError,          # 店铺存在、auth_status != 'expired'、auth_type='api'
    items: [{
      productId, ready: bool,
      blockers: [ "未匹配 Ozon 类目，请先在编辑页选择类目",
                  "必填属性缺失: Бренд(85)、Пол(..." ],
      warnings: [ "图片 3 为防盗链代理 URL，发布时将自动转存" ]
    }]
  }
```

**校验项实现全部复用现有代码**（关键：preflight 是只读预演，不建任务、不调 Ozon 写接口）：

| 校验项 | 复用 |
|---|---|
| 店铺授权状态/类型 | `Store.find_by_store_id` + M1 的 `auth_status` |
| 类目已匹配 | `descriptionCategoryId/typeId` 非空（`product_routes.py:84` 的 ID 归一逻辑复用） |
| 必填属性完整 | `validate_ozon_product_items`（`publish_service.py:834`）改为可独立调用的纯函数（现状已接近纯函数，仅需去副作用） |
| 图片可发布性 | 首图存在 + URL 类型判断（`_is_public_cdn_url` / `/uploads/` / base64 检测，`app.py:289` 同款逻辑抽公共函数） |
| 价格/SKU 就绪 | `price > 0`、`_valid_skus`（`publish_service.py:2069`）、`skuCode` 唯一性（`ensure_platform_sku_codes` 的 dry-run 模式） |
| 币种 | `_get_store_currency(store_id)`（`publish_service.py:1792`）非空 |

**前端接入**（`collect.js` 发布流程，`:4905` publishProduct / `:4765` 保存并发布）：

```
选店铺弹窗确认 → 调 preflight →
  全部 ready     → 继续 POST /api/publish（现逻辑不变）
  有 blockers    → 弹窗逐商品列出问题，提供「去编辑」跳转（打开产品编辑弹窗并锚点到对应区块）
  仅 warnings    → 黄色提示，用户可选择继续
```

扩展端 `publish-modal.js` 同步接入（提交前先调 preflight，逻辑同上）。

#### 4.2.1 修复上架记录页提交链路（P0 bug，v2 新增）✅ 已实施

**问题**：上架记录页「提交发布/批量提交」（`frontend/js/pages/publish.js:284` → `POST /api/publish-records/<id>/submit`，`publish_record_routes.py:171`）调用 `PublishService.create_task(product_id, platform)` 时**未传 `store_id`**，而 `create_task` 在 `publish_service.py:2755-2756` 已强制校验无 store_id 即抛错 → 该入口提交的记录 100% 立即失败，错误信息为「请选择要发布到的 Ozon 店铺」。批量提交端点（`publish_record_routes.py:279`）同样问题。

**修复**（三处，均为小改）：

1. `publish_record_routes.py:185` / `:279`：`create_task(product_id, platform, store_id=record.get('storeId'))`，顺带透传 `record.get('publishMode')`；记录缺 storeId 时返回明确错误「该记录未指定店铺，请编辑记录选择店铺」而不是让 create_task 抛通用错误。

## 七、风险与后续项（不阻塞 MVP）

1. **扩展→后端免鉴权**：`core/api-client.js` 用 `credentials:'omit'` 直连生产 API（`https://ozon.wangyaojun.cn`），任何人可调采集/发布接口。前端 `api.js` 虽带 Bearer token，但后端无校验中间件。建议 M4 加共享令牌（扩展 options 页配置 + 后端 `before_request` 校验 `X-Api-Token`），CORS 白名单不构成鉴权。
2. **商品 JSON 文件存储**：`products.json` 单文件全量内存 + 线程锁（`models/product.py`），数据量上万后写入与加载变慢，且多进程部署（gunicorn 多 worker）有丢写风险。当前 `wsgi.py` 单进程可容忍；建议后续迁 SQLite（stores/类目已在 SQLite，模式现成）。
3. **店铺日限额**：`today_limit` 字段存在但无执行逻辑。若需要，在 `create_task` 前统计当日该店铺任务数拦截（依赖 PublishRecord 按店铺+日期计数）。
4. **Ozon 端点版本**：`/v1/seller/info`（官方 SellerAPI_SellerInfo）为首选探测端点；若版本变动返回 404/405 则自动降级 `/v3/product/list`（见 4.1.1）。该接口不返回店铺数字 ID，故 store_id 仍取用户填写值。
