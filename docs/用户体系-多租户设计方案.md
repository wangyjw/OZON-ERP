# 用户体系与多租户设计方案

- 需求单号：XQ26091901-用户体系搭建
- 参考对象：[JSH_ERP](https://gitee.com/jishenghua/JSH_ERP)（单库共享表 + `tenant_id` 行级隔离 + 角色/功能权限模型）
- 状态：方案评审稿（不含实现代码）
- **已决策**：管理后台采用**自建轻量 admin 后台**（§6 方案 B），不部署 JSH_ERP；JSH_ERP 仅作模式参考，其集成评估（§6.6/§6.7）留档备查

---

## 1. 现状与差距

| 维度 | 现状 | 差距 |
|---|---|---|
| 登录认证 | `/api/auth/login` 不校验密码、自动建用户；token 存内存 dict，重启失效 | 无真实认证；无会话持久化 |
| 用户模型 | `accounts` 表已有（PBKDF2 密码哈希、admin/operator 角色、status），但 `auth_routes` 并未使用它；`users.json` 的 `User` 模型是另一套游离数据 | 两套用户数据并存，需归并到 `accounts` |
| 租户概念 | 无租户表；`stores.account_id` 已预留归属字段 | 缺租户层，无法 SaaS 化 |
| 数据隔离 | 商品/发布任务/发布记录存在 JSON 文件，无归属字段；SQLite 各业务表无 `tenant_id` | 所有数据全局共享 |
| 接口鉴权 | 前端已带 `Authorization` 头，后端无校验 | 全部接口裸奔 |
| 权限体系 | `accounts.role` 只有 admin/operator，无菜单/按钮级权限 | 无 RBAC |
| 前端 | 无登录页、无路由守卫、无用户/租户管理页 | 需新增 |

**结论**：地基比想象中好——`accounts` 表、密码哈希、密钥加密、前端 token 注入都已具备。本方案的核心工作是：**补租户层 + 真认证 + 全量数据加 `tenant_id` 隔离 + JSON 数据入库 + RBAC**。

## 2. 总体架构

```
┌─────────────────────────────────────────────────────┐
│  前端 (SPA, hash router)                              │
│  登录页 → 路由守卫 → 菜单/按钮按权限渲染                │
├─────────────────────────────────────────────────────┤
│  Flask 后端                                           │
│  auth 中间件(before_request)                           │
│    └─ 解析 token → g.user / g.tenant_id / g.perms      │
│  routes → service/model 层                             │
│    └─ 所有查询强制追加 tenant_id 过滤                   │
├─────────────────────────────────────────────────────┤
│  SQLite geekozon.db                                   │
│  tenants / accounts / roles / account_role /          │
│  permissions / role_permission / sessions /           │
│  stores / products / publish_tasks / ... (均带租户列)  │
└─────────────────────────────────────────────────────┘
```

参考 JSH_ERP 的核心做法：

- **隔离方式：单库共享表 + `tenant_id` 列**（而非分库分表）。SQLite 单文件、租户量级小（几十~几百），行级隔离成本最低，迁移最简单。未来量大再演进到分库，接口层不变。
- **权限方式：角色 → 功能权限映射**（JSH_ERP 的 user_business 思路），落到 `role_permission` 关系表，权限粒度到"菜单 + 操作按钮"。
- **三级角色**：`super_admin`（平台运营方，跨租户）→ `tenant_admin`（租户管理员，管本租户用户/店铺/数据）→ `operator`（操作员，按分配的功能权限干活）。

## 3. 数据模型设计

### 3.1 新增表

```sql
-- 租户表（平台侧管理的"公司/客户"）
tenants (
    id            INTEGER PK,
    name          TEXT NOT NULL,            -- 租户名称（公司名）
    code          TEXT NOT NULL UNIQUE,     -- 租户编码（登录时可用于定位）
    status        TEXT NOT NULL DEFAULT 'active',   -- active / disabled / expired
    expire_at     TEXT,                     -- 到期时间（SaaS 收费用，可空=不限）
    quota_users   INTEGER NOT NULL DEFAULT 10,      -- 用户数配额
    quota_stores  INTEGER NOT NULL DEFAULT 20,      -- 店铺数配额
    remark        TEXT NOT NULL DEFAULT '',
    created_at / updated_at
)

-- 账号表：在现有 accounts 上扩展（见 3.2）
-- 角色表
roles (
    id          INTEGER PK,
    tenant_id   INTEGER,                    -- NULL = 平台预置角色
    code        TEXT NOT NULL,              -- super_admin / tenant_admin / operator / 自定义
    name        TEXT NOT NULL,
    is_system   INTEGER NOT NULL DEFAULT 0, -- 系统预置不可删
    UNIQUE(tenant_id, code)
)

-- 账号-角色关联（一个账号可挂多个角色，默认一个）
account_role (
    account_id  INTEGER NOT NULL,
    role_id     INTEGER NOT NULL,
    PRIMARY KEY (account_id, role_id)
)

-- 权限点表（菜单/按钮/接口 三类，预置，平台级）
permissions (
    id        INTEGER PK,
    code      TEXT NOT NULL UNIQUE,         -- 如 product:view / product:edit / store:verify
    name      TEXT NOT NULL,
    type      TEXT NOT NULL,                -- menu / action / api
    parent_id INTEGER                       -- 树形，对应左侧菜单结构
)

-- 角色-权限关联
role_permission (
    role_id       INTEGER NOT NULL,
    permission_id INTEGER NOT NULL,
    PRIMARY KEY (role_id, permission_id)
)

-- 会话表（替代内存 _token_store，重启不失效）
sessions (
    token      TEXT PK,                     -- 随机 token 或 JWT jti
    account_id INTEGER NOT NULL,
    tenant_id  INTEGER,                     -- NULL = 平台超管会话
    expires_at TEXT NOT NULL,
    created_at TEXT NOT NULL
)

-- 管理审计日志（admin 后台操作 + 租户内敏感操作留痕）
audit_logs (
    id               INTEGER PK,
    actor_account_id INTEGER NOT NULL,      -- 操作人
    actor_name       TEXT NOT NULL DEFAULT '',
    tenant_id        INTEGER,               -- 受影响租户（可空）
    action           TEXT NOT NULL,         -- tenant.create / user.reset_password / store.delete ...
    target_type      TEXT NOT NULL DEFAULT '',  -- tenant / account / store / session
    target_id        TEXT NOT NULL DEFAULT '',
    detail           TEXT NOT NULL DEFAULT '{}', -- 变更明细 JSON
    created_at       TEXT NOT NULL
)
```

### 3.2 现有表扩展

| 表 | 变更 |
|---|---|
| `accounts` | 新增 `tenant_id INTEGER`（迁移时归默认租户；`is_super=1` 的平台账号可空）；新增 `is_super INTEGER NOT NULL DEFAULT 0`（平台超管标记，见 §6）；`role` 字段保留兼容，真实权限走 `account_role`；`username` 唯一约束改为 `(tenant_id, username)` 联合唯一 |
| `stores` | 新增 `tenant_id`（跟随所属 account 的租户；公共店铺仍可用 `account_id IS NULL` + `tenant_id` 表达"租户内公共"）；`store_id` 唯一约束放宽为 `(tenant_id, store_id)` 联合唯一——两个客户绑同一个 Ozon 店铺是合法场景 |
| `ozon_sku_data` / `product_favorites` / `gallery_assets` / `watermark_templates` / `selection_rules` | 新增 `tenant_id`，数据按租户隔离 |
| `pricing_config` / `category_commissions` / `shipping_templates` | 新增 `tenant_id`，每个租户一套定价参数（`pricing_config` 由单行变每租户一行） |
| `ozon_categories` / `ozon_category_attributes` / `ozon_attribute_dictionary_values` / `category_mappings` | **不加租户列**——Ozon 官方类目字典是全局共享数据，各租户只读 |
| `pricing_history` | 新增 `tenant_id` + `account_id`（谁测的价可审计） |

### 3.3 JSON 文件数据入库（前置工程）

当前 `products.json` / `publish_tasks.json` / `publish_records.json` / `users.json` 由 `BaseModel` 内存缓存 + 文件落盘，**无法做行级租户过滤，且有并发丢数据隐患**。方案：

- 新增 `products` / `publish_tasks` / `publish_records` 三张 SQLite 表，字段以 TEXT/JSON 列承载现有弹性结构（`payload TEXT` 存完整 JSON + 常用字段提为列：`tenant_id`、`account_id`、`status`、`store_id`、`created_at`），保持前端数据契约不变。
- 启动时一次性迁移：读 JSON → 写入默认租户 → 原文件改名 `.bak`。
- `User`（users.json）废弃，统一并入 `accounts`。
- `Notice` 公告改为平台级（带 `tenant_id` 可空：NULL=全平台公告，有值=租户内公告）。

## 4. 认证与会话

### 4.1 登录流程

```
POST /api/auth/login  { username, password, tenantCode? }
  1. 定位账号：tenantCode 指定租户；未指定时若用户名全局唯一则直接命中，
     多租户重名则返回候选租户列表让前端再选（或强制要求填租户码）
  2. Account.verify_password() 校验（现有 PBKDF2 逻辑直接复用）
  3. 检查 tenant.status == active 且未过期
  4. 创建 sessions 记录，token = secrets.token_hex(32)
  5. 返回 { token, user: {id, username, nickname, roles, permissions, tenant:{id,name}} }
```

- **登出** `/api/auth/logout`：删 session。
- **会话校验**：`/api/auth/me` 返回用户 + 权限点列表 + 租户信息，前端启动时调用恢复登录态。
- Token 有效期沿用 `Config.TOKEN_EXPIRE_HOURS`（24h），可选滑动续期。
- 密码策略、登录失败锁定（连续 5 次锁 10 分钟）作为二期增强项列入 backlog。

### 4.2 鉴权中间件

`before_request` 全局拦截 `/api/*`：

1. 白名单放行：`/api/auth/login`、`/api/health`、`/api/extension/*`、图片代理/上传回显（按需）。
2. 解析 `Authorization: Bearer <token>` → 查 `sessions` → 加载 account + roles + permissions → 挂到 `flask.g`：
   - `g.account`（含 `tenant_id`）
   - `g.perms`（权限点 code 集合）
   - `g.is_super`（super_admin 标记）
3. 无 token / 过期 / 账号停用 / 租户停用 → 401，统一错误码格式。
4. 提供装饰器 `@require_perm('product:edit')` 做接口级授权；`super_admin` 自动放行所有权限。

### 4.3 租户上下文注入（隔离的关键）

定义统一约定，**消灭"忘了加 where tenant_id"的漏洞**：

- model/service 层所有查询函数第一个参数收 `tenant_id`（从 `g.account` 取），super_admin 传 `None` 表示跨租户。
- 提供一个 `tenant_scope(table_alias)` 拼 SQL 的小工具 + `TenantModel` 基类（封装 find_all/create/update/delete 自动带租户条件）。
- 写操作时 `tenant_id` 只允许由服务端注入，**忽略请求体里的 tenant_id/accountId 字段**（防止越权塞数据）。
- `store_id`/`accountId` 等前端入参先校验归属：目标行 `tenant_id != g.account.tenant_id` → 404（不暴露存在性）。

## 5. 权限模型（RBAC，对齐 JSH_ERP）

JSH_ERP 用 user_business 挂"角色→功能权限"关系，本方案等价物为 `roles` + `role_permission` + `permissions`。

### 5.1 权限点（预置，type=menu/action）

按现有 9 个前端页面划分菜单权限，每菜单下挂操作权限：

| 菜单 (menu) | 操作 (action) 示例 |
|---|---|
| home 首页 | — |
| collect 采集箱 | collect:view / collect:import / collect:delete / collect:assign |
| publish 刊登 | publish:view / publish:submit / publish:cancel |
| online-products 在线商品 | online:view / online:sync / online:edit |
| store 店铺 | store:view / store:bind / store:verify / store:delete |
| model 财务/定价 | pricing:view / pricing:edit |
| media 图库/水印 | media:view / media:upload / media:delete |
| ai-write AI 文案 | ai:use |
| calculator 定价计算器 | calc:use |
| **新增 system 系统管理** | user:manage / role:manage / tenant:manage(仅超管) / notice:manage |

### 5.2 预置角色

| 角色 | tenant_id | 权限 |
|---|---|---|
| super_admin | NULL | 全部 + tenant:manage |
| tenant_admin | NULL（模板）/ 实例化到各租户 | 除 tenant:manage 外全部 |
| operator | NULL（模板） | collect/publish/online/media/ai/calc 的 view+操作，无 system、无 pricing:edit |

租户自定义角色：`tenant_admin` 可在本租户内新建角色并从权限点中勾选（前端渲染成权限树）。

### 5.3 数据级权限（可选二期）

JSH_ERP 还有"按部门/业务员看数据"的维度。本 ERP 对应场景是"操作员只能看分配给自己的商品/店铺"——`products.assignee`、`stores.account_id` 字段已存在，二期加 `data_scope`（all / assigned / self）到角色即可，一期先全员可见本租户数据。

## 6. 平台管理后台（Admin Console）

需求点："后台管理所有用户"——即平台运营方用的**超级管理后台**，面向 `super_admin`，与租户使用的 ERP 前台是两个界面、两套功能。

### 6.1 形态选型

| 方案 | 说明 | 评价 |
|---|---|---|
| A. 同 SPA 内加 `#/admin` 区域 | 超管登录后看到额外菜单组 | 改造最小，但超管与租户用户共用一个壳，权限边界靠前端隐藏，不够干净 |
| **B. 独立入口 `admin.html`（已选定）** | Flask 静态目录新增 `frontend/admin/`（或 `admin/` 独立目录），访问 `/admin` 打开独立登录页与控制台；接口走 `/api/admin/*` 命名空间 | 超管完全看不到租户业务 UI；JSH_ERP 也是"系统管理"独立模块的思路；两套前端可复用 `api.js`/样式 |

推荐 B：**同一个 Flask 进程、同一个 SQLite 库**，只是前端多一个入口页面 + 后端多一个 admin 蓝图。不引入新服务、不改部署形态。

### 6.2 后台功能清单

```
admin 控制台
├── 仪表盘        租户数 / 用户总数 / 店铺总数 / 近30天发布量 / 到期预警
├── 租户管理      开通租户(自动建 tenant_admin) / 编辑 / 停用 / 到期时间 / 配额调整
├── 用户管理      跨租户查看全部账号：搜索 / 按租户筛选 / 重置密码 / 启停 / 改角色
│                └── 进入某租户详情 → 该租户的用户/店铺/数据量一览
├── 角色权限      平台预置角色模板维护 + 权限点清单查看
├── 会话管理      在线会话列表 / 强制下线（删 session）
├── 公告管理      发布全平台公告 / 指定租户公告（对应 notices.tenant_id）
└── 审计日志      管理操作全留痕（谁、何时、对哪个租户/用户、做了什么）
```

### 6.3 接口命名空间

新增 `admin_routes` 蓝图，全部挂 `/api/admin/*`，统一要求 `super_admin`：

| 接口 | 说明 |
|---|---|
| `GET /api/admin/dashboard` | 平台级统计 |
| `GET/POST/PUT /api/admin/tenants` `PUT .../:id/status` | 租户 CRUD、启停、配额、到期 |
| `GET /api/admin/users?tenantId=&keyword=` | 跨租户用户列表 |
| `POST /api/admin/users/:id/reset_password` `.../status` `.../roles` | 重置密码、启停、调角色 |
| `GET/DELETE /api/admin/sessions` | 会话查看与强制下线 |
| `GET/POST /api/admin/notices` | 平台公告 |
| `GET /api/admin/audit_logs` | 审计日志查询 |

权限校验：不用权限点逐条勾，直接 `@require_super`——超管是平台唯一角色，天然全权限；`tenant_admin`/`operator` 调 `/api/admin/*` 一律 403。

### 6.4 配套表变更

- 新增 `audit_logs`：`id / actor_account_id / actor_name / action / target_type / target_id / detail(JSON) / tenant_id / created_at`，admin 操作 + 租户内敏感操作（删店铺、重置密码）都写入。
- `notices` 入库时加 `tenant_id`（NULL=全平台公告，供 admin 后台广播用，见 §3.3）。
- 角色判定：`accounts.is_super` 布尔列比"建一个 super_admin 角色再关联"更直接——`is_super=1` 的账号不归属任何租户（`tenant_id` 可空），登录后端识别后引导到 `/admin` 入口。

### 6.5 登录与分流

- `/admin` 页面有自己的登录表单；提交到同一个 `POST /api/auth/login`。
- 后端返回的 user 里带 `isSuper` 标记：超管从租户前台登录 → 前端提示并跳转 `/admin`；非超管在 admin 页登录 → 拒绝（"该账号无平台管理权限"）。
- 超管会话与租户会话共用 `sessions` 表（`tenant_id` 存 NULL）。

### 6.6 备选评估：直接部署一套 JSH_ERP 作为后台（已否决，留档）

> **决策记录（2026-09）**：经评估选用方案 B 自建轻量后台，本节与 §6.7 仅作留档——若未来组织建设统一账号中台或引入进销存系统，再回来参考。

**结论：可行，但不推荐作为默认路径。** JSH_ERP 开箱只能管理它自己的库（`jsh_user`/`jsh_role`/`jsh_tenant`/`user_business`），并不认识本系统的 `accounts`/`tenants`/`stores`——部署一套原样 JSH_ERP 对 OZON-ERP 的管理能力是零。要让它真正"管这个 ERP"，必须在两套系统之间写集成层，且还要新增 JVM + MySQL 整套运维栈。

#### 两种集成模式

**模式一：JSH_ERP 做主数据源 + 定时同步**

```
JSH_ERP (Java + MySQL)              GeekOzon (Flask + SQLite)
┌─────────────────────┐            ┌──────────────────────────┐
│ jsh_user / jsh_role │ ──定时同步─→│ accounts / tenants (副本) │
│ jsh_tenant          │  直连MySQL  │ 本地 stores/products 等   │
│ user_business(权限) │  或调API   │ 仍由本系统自己管理        │
└─────────────────────┘            └──────────────────────────┘
```

- 用户在 JSH_ERP 里维护，同步任务把 user/tenant 映射写入本地表。
- 硬伤：**密码哈希不兼容**——JSH 用 MD5（登录名+密码），本地用 PBKDF2；同步密码要么降级存 MD5 要么放弃本地校验。且数据有时延、停用/删除靠状态对齐，容易出"JSH 里删了但本地还能登录"的窗口期。

**模式二：JSH_ERP 做身份源（联邦登录）**

```
用户 → GeekOzon 登录页 → /api/auth/login
                            │ 转发凭证
                            ▼
                     JSH_ERP /user/login 校验
                            │ 返回用户+租户信息
                            ▼
                     按 tenantId 映射本地租户 → 发本地 session
```

- GeekOzon 不存密码，认证只有一处，相对干净。
- 仍需自研：登录代理、tenant/account 映射同步、is_super 判定映射、JSH token 失效联动。
- 租户内的店铺/商品/发布数据过滤**仍然在 GeekOzon 本地做**——JSH 只回答"这个人是谁、属于哪个租户"，数据隔离的活一点没少。

#### 成本对比

| 项 | 自建 admin 后台（方案B） | 部署 JSH_ERP |
|---|---|---|
| 新增运行时 | 无（同 Flask 进程同库） | JDK + MySQL 5.7+ (+Redis) + 反向代理 |
| 需写代码 | admin 页面 + `/api/admin/*`（约 7 个模块） | 集成层（登录代理/同步/映射）+ 可能的 JSH 二开 |
| 权限模型 | 按本系统页面定制 | 现成但需逐条映射到本系统权限点 |
| 数据隔离 | 本系统内闭环 | 集成层只解决"身份"，租户过滤照样要写 |
| 界面 | 需开发 | 现成（Vue2+Antd：用户/角色/机构/日志/租户） |
| 后续维护 | 随本系统演进 | 跟随 JSH 上游升级 vs 分叉维护 |
| 合规 | 自有代码 | JSH_ERP 为 GPL 系开源协议，商用/二开需核实授权条款 |

#### 什么情况下值得选 JSH_ERP

- 组织**已经在用** JSH_ERP 做统一账号/组织目录，本系统只是接入方；
- 未来规划多套内部系统共享同一用户体系，需要中心化 IdP；
- 团队本就是 Java 技术栈，运维 MySQL 无负担。

以上任一不满足，自建轻量后台（方案 B）都是更省的选择——它只解决本系统需要的那 7 个管理模块，不引入异构栈。

### 6.7 业务数据集成：把 OZON-ERP 的数据接入 JSH_ERP

> 用户追问："能不能把 ERP 的数据与 JSH 的进行集成呢？" —— 这里的"集成"有两种完全不同的含义，先拆开：

| 含义 | 目标 | 性质 |
|---|---|---|
| **身份/组织数据集成** | 用户、租户、角色共用一份 | §6.6 已评估（联邦登录或主数据同步） |
| **业务数据集成** | OZON-ERP 的商品/店铺/发布数据出现在 JSH_ERP 里（或反之） | 本节评估 |

#### 先看两边数据的"可映射度"

| OZON-ERP | JSH_ERP 对应物 | 匹配度 |
|---|---|---|
| stores（Ozon 店铺授权） | 无直接对应；最接近"供应商/客户"或自定义 | ✗ 领域不同 |
| products（采集箱 1688 商品） | jsh_material（商品/物料） | ◐ 字段 40% 重叠，结构差异大（skuList/attributes 嵌套 vs JSH 的 material+unit+extend） |
| publish_tasks/records（刊登任务） | 无对应（JSH 没有"平台刊登"概念） | ✗ |
| online_products（Ozon 在售商品） | 无对应 | ✗ |
| pricing_config/history（定价） | 无对应；可折算进单据 | ✗ |
| selection_rules/favorites（选品） | 无对应 | ✗ |
| accounts/tenants | jsh_user/jsh_tenant | ◐ §6.6 已覆盖 |

**结论**：两个系统业务领域其实**正交**——OZON-ERP 管"采集→刊登→在售"的跨境运营链路，JSH_ERP 管"进销存+财务"的内部账务链路。能真正对接的只有两端都有的"商品/物料"概念和"单据"概念。

#### 可行的业务集成场景（按价值排序）

**场景 1：OZON 商品 → JSH 物料档案同步**（推荐，单向）

- 把 `products`（已编辑完成的刊登品）按映射规则写入 JSH 的 `jsh_material`：title→name、类目→categoryId（需建映射表）、重量/尺寸→扩展字段、SKU 行→jsh_material_extend（条码/价格/库存）。
- 方式：OZON-ERP 侧做一个"同步到 JSH"任务（读 JSH 开放的 REST API 或直写 MySQL），幂等键用 `productId`。
- 价值：发布出去的货在 JSH 里有物料档案，后续进销存单据能挂得上。
- 成本：1 个映射配置表 + 1 个同步服务（约 1 个接口对接工作量）。

**场景 2：刊登成功 → 自动生成 JSH 期初库存/采购单**（可选）

- `publish_records` 状态变 `published` 时，回调 JSH 生成一张"其他入库单"或挂在"采购单"下，让这批货进入 JSH 的库存视图。
- 价值：库存账在 JSH 一处看；适合"OZON 管卖、JSH 管账"的协作模式。
- 成本：需理解 JSH 单据模型（单据头+单据体+审核流程），工作量中等，且要处理 Ozon 订单回流时扣减（JSH 没有 Ozon 对接，订单要另行集成）。

**场景 3：数据库层共享/视图打通**（不推荐）

- 让 JSH 直接读 OZON 的 SQLite（JSH 是 MySQL，跨库引擎不通）；或把 OZON 数据镜像到 MySQL 建视图给 JSH 报表用。
- 只读报表场景可以接受（镜像表给 BI），但**不要**让 JSH 的写流程碰到 OZON 的表。

#### 集成边界建议（不管选哪条路都要守）

1. **单向同步、明确主从**：每条数据只能有一个"主库"——用户/租户若以 JSH 为主，则 OZON 侧只读；商品若以 OZON 为主，则 JSH 的 jsh_material 对应记录标记来源、禁止在 JSH 侧改（或改了不回传）。
2. **走 API 不走直连库**：JSH_ERP 有标准 REST 接口（`/material/add` 等，需 JWT/租户上下文），优先调 API；直写 MySQL 绕过了 JSH 的校验逻辑，容易写出脏单据。
3. **幂等与对账**：同步用业务键幂等（OZON productId ↔ JSH material 的自定义字段存映射），失败进重试队列，定期对账报表。
4. **凭证不要互传**：`stores.api_key`/`seller_cookies` 是 OZON 侧加密资产，集成层绝不同步这类敏感字段。

#### 分期建议（若确定走 JSH 集成路线）

| 阶段 | 内容 |
|---|---|
| I1 | 身份联邦打通（§6.6 模式二）——先让"同一个人"两边能登录 |
| I2 | 商品物料单向同步（场景 1）——最小可用集成 |
| I3 | 刊登→库存单据联动（场景 2）——打通"卖"与"账" |
| I4 | Ozon 订单→JSH 销售单回流（新课题，不在本需求范围） |

注意：I2/I3 依赖 I1 的租户映射先落地（JSH 单据都带 tenantId，得知道"这条数据写给哪个租户"）。

## 10. 数据迁移与兼容策略

`db.py` 的 `_run_migrations` 已有幂等迁移模式，沿用：

1. 建新表（IF NOT EXISTS）：`tenants`, `roles`, `account_role`, `permissions`, `role_permission`, `sessions`, `audit_logs`。
2. `accounts` 加 `tenant_id` 与 `is_super`：创建**默认租户** `default`（ID=1），所有存量 account 归入；建立 `(tenant_id, username)` 联合唯一索引。
3. `stores` 加 `tenant_id`：跟随其 `account_id` 所属租户；`account_id IS NULL` 的归默认租户。
4. 各业务表 ALTER ADD `tenant_id NOT NULL DEFAULT 1`。
5. **JSON→SQLite 迁移与回滚防线**：
   - 随 `init_db` 执行一次：读取 `products.json` / `publish_tasks.json` / `publish_records.json`，每条记录写入对应新 SQLite 表，补全 `tenant_id=1` 与对应 `account_id`。
   - 数据入库检验数量匹配后，原 JSON 文件改名为 `*.json.bak.<timestamp>`，保留至少 30 天，**严禁物理删除**。
   - 保留快速回退机制：如新版本上线后发现入库异常，可切换配置一键切回 JSON 模式读取。
6. 预置角色/权限点 INSERT OR IGNORE；存量 admin → tenant_admin 角色，operator → operator 角色。
7. **超管引导与初始化**：提供 CLI 命令 `python -m backend.cli create-super --username admin --password xxx`，或者首次启动时若库内无 `is_super=1` 账号且检测到环境变量 `SUPER_ADMIN_PASSWORD` 时自动创建，控制台打印首次初始化提示。

## 11. 浏览器扩展 (Chrome Extension) 适配方案

采集箱依赖 Chrome 插件向后台发送采集数据，是数据流入的关键一环：

1. **现状**：插件当前直接向 `/api/products` 发 POST，无认证头，任何人或恶意请求可刷接口。
2. **凭据注入与存储**：
   - 用户在 ERP Web 端登录后，网页提供“同步凭证到插件”功能（或插件 Popup 弹窗输入 ERP 账号密码直接登录）。
   - 插件将返回的 `token` 及 `tenantCode` 存入 `chrome.storage.local`。
3. **请求拦截注入**：
   - 插件 background / content script 请求后端时，统一注入 `Authorization: Bearer <token>` 与 `X-Tenant-Code` 头。
4. **失效处理**：
   - 若后端返回 401，插件弹出桌面通知提示“ERP 登录已过期，请重新登录插件或在 ERP 页面同步凭证”，停止采集上传，避免脏数据提交。

## 12. 安全与防御策略

- `SECRET_KEY` 生产必须显式配置（sessions + encrypt_secret 都依赖它），现有告警逻辑保留。
- token 用 `secrets.token_hex(32)`，不 JWT——SQLite 会话表天然支持服务端吊销，复杂度低；后续多实例部署再换 JWT。
- 所有越权访问返回 404 而非 403（不泄露资源是否存在）。
- `stores.api_key`/`seller_cookies` 的 `encrypt_secret` 加密维持现状；租户隔离后更要确保 A 租户接口绝不返回 B 租户店铺字段。
- 管理类接口（user/role/tenant）必须走 `@require_perm`，不能只靠前端隐藏按钮。
- 登录接口加简单限流（每 IP 每分钟 10 次），防爆破；连续 5 次密码错误锁定 10 分钟。

## 14. 风险、开放问题与已决项

1. **JSON 入库**是工作量最大的单项（products 结构深、skuList/attributes 嵌套多），保留 `payload` JSON 列整体承载、只把过滤/排序字段提为列，避免大拆大改。
2. **用户名唯一性**：确定采用租户内唯一 `(tenant_id, username)`，登录界面支持租户码；超管账号平台唯一。
3. **一个账号属于多个租户**：一期不做，一账号一租户；有需求时再扩展。
4. **浏览器扩展凭证**：已补充 §11 方案，M2 阶段一并打通。
5. **配额/到期控制**：到期后租户账号可登录，但写操作（发刊登、绑店铺、采集商品）均拦截提示“租户服务已到期，请联系平台续费”，控制台顶部展示到期警示横幅。
6. **超管账号初始化**：确定采用 CLI 命令 + 环境变量启动时兜底创建（§10 第 7 步）。
7. **管理后台形态（已决策）**：确定选择方案 B（自建轻量 admin 后台），不部署 JSH_ERP，与主工程同一进程同一数据库，降低整体交付与运维负担。
